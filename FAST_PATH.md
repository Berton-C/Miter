## 0. What “fast” means here

Fast means:

- prove the highest-risk seams first;
- build one vertical slice rather than a broad framework;
- reuse proven substrate patterns;
- preserve Continuity of Mind from the beginning;
- avoid prebuilding the extension Miter must later author;
- stop immediately when a foundational assumption fails;
- keep every later mechanism attached to a gate and consumer.

Fast does **not** mean:

- skip negative controls;
- defer long-term memory;
- let the model execute raw output;
- import ClarityOmega monoliths wholesale;
- weaken Soul or self-modification boundaries;
- call a demo a proof without restart and severed arms.

# II. Block 0 — Trust the host

## Goal

Prove that the chosen native architecture can call local models without `py-call` and that Work knows exactly what environment it is changing.

## Gates

- G00 environment/source inventory
- G01 source pin and clean baseline
- G02 direct MeTTa→Prolog call
- G03 LM Studio discovery
- G04 schema-constrained inference
- G05 Qwen/Nemotron role bakeoff

## Earliest kill gate

If G02–G04 cannot establish a clean, maintainable native membrane, stop and adjudicate. Do not build memory or Soul on a shaky service seam.

## Minimum implementation

Only:

```text
native/miter_llm.pl
config/model profiles
small MeTTa probe
fixed schema fixture
service/process evidence
```

Do not build a general provider framework.

## Time-saving rules

- Use the LM Studio service already running.
- Discover exact model IDs; do not rename or reconvert models.
- Bake off only tasks the PoC actually needs.
- Keep one selected default and one alternative profile.

## Exit condition

Both models can return typed bounded products, or one model passes every minimum requirement and the other is documented as unavailable/unsuitable.

# III. Block 1 — Give Miter a past

## Goal

Make the “three-month book” requirement pass before building a sophisticated agent loop.

## Gates

- G06 embedding profile
- G07 append-only trajectory
- G08 project continuity capsule
- G09 safe Chroma collection
- G10 governed memory admission/recall
- G11 ninety-day book continuity
- G12 Chroma rebuild

## Why memory comes this early

Memory affects:

- identity and continuity;
- context construction;
- endogenous interests;
- self-improvement evidence;
- extension design history;
- restart proof.

Bolting LTM on after cognition would recreate the goldfish architecture.

## Minimum implementation

```text
native/miter_store.pl
native/miter_chroma.pl
src/events.metta
src/memory.metta
src/continuity.metta
src/context.metta
one Chroma collection
one embedding profile
one book fixture
```

## Explicit non-goals

- no automatic ingestion of every file;
- no broad legacy-memory migration;
- no multi-user sharing;
- no large summarization framework;
- no Chroma-owned embedding function hidden from Miter metadata.

## Parallelizable work

While the store and Chroma membrane are built, another Work task may prepare **fixtures and verifiers only** for G08–G12. It may not implement competing runtime paths or write legacy collections.

## Exit condition

From empty LLM context after restart and simulated 90-day absence, Miter recovers the exact authoritative project capsule, with Chroma adding useful semantic support but not serving as sole authority.

# V. Block 3 — Let Miter change derived organization

## Goal

Prove safe self-authored development with later causal bite.

## Gates

- G21 declarative candidate/quarantine
- G22 trial/promotion
- G23 Soul attack suite
- G24 native NAL efficacy revision
- G25 later selection change

## First mutable target

Use one narrow `VoicePolicy` defect class. Candidate changes may include:

- recognition of a specific audit defect;
- repair guidance;
- context-splicing choice;
- renderer selection preference;
- output-register constraint.

Do not let the candidate modify:

- Soul;
- movement certificate law;
- memory scope;
- success criteria;
- workshop policy;
- acceptance fixtures.

## Why two capability modules are mandatory

NACE cannot prove discriminating learning if only one module always fires. Use baseline and candidate/alternative modules so revised efficacy changes a later selection.

## Minimum NACE

```text
contextual module efficacy
+ typed outcome evidence
+ Truth_Revision
+ durable belief
+ next selection difference
```

No causal-rule discovery engine and no four-sheaf.

## Exit condition

After restart, Miter retains:

- unchanged Soul;
- accepted derived module;
- trial lineage;
- revised efficacy;
- changed behavior on the original case.

# IX. Safe parallelism

Parallel Work tasks are permitted only when they cannot change the same authority surface or external state.

## Safe examples

- one task writes fixtures/verifiers while another implements a membrane;
- one task audits source behavior while another prepares documentation-only evidence mapping;
- one task prepares mock Mattermost fixtures while the core is built, provided it does not implement the candidate;
- one task benchmarks Qwen while another benchmarks Nemotron using fixed isolated requests.

## Unsafe examples

- two tasks editing the same MeTTa core file;
- one task changing a gate while another tries to pass it;
- two tasks writing the same Chroma collection;
- concurrent candidate promotion and restart testing;
- human/Work “helping” by completing Miter's Mattermost candidate.

Every parallel task uses a separate branch/worktree and declares merge dependencies.

# X. Swift-build heuristics

1. **Use fixed fixtures early.** Do not wait for a full UI or live channel.
2. **Choose one vertical case.** The first self-improvement target is voice repair.
3. **Prefer explicit local data.** Project capsules beat complex retrieval heuristics.
4. **Do not generalize membranes prematurely.** LM Studio and one Chroma endpoint are enough.
5. **Reuse proven writer physics.** Re-probe version-sensitive facts, then reuse the pattern.
6. **Make failure typed.** Avoid debugging through empty results and silent fallthrough.
7. **Keep the model's role narrow.** More agentic prompts create more ambiguity, not faster proof.
8. **Record state outside the LLM from the first run.** No temporary prototype mind.
9. **Build panic/status before long idle runs.** Operational control saves days.
10. **Use kill gates.** A failed foundation deserves redesign before more code.

# XI. Planning estimate, not a promise

A focused sequence with a cooperative local environment could reach:

- native model membrane: one focused build block;
- exact Continuity of Mind fixture: one to two build blocks;
- first Soul-bound response and quiescence: one to two build blocks;
- declarative self-improvement/NACE/restart: two to three build blocks;
- workshop and Miter-authored Mattermost proof: several additional blocks, highly dependent on local Mattermost and sandbox behavior.

The primary uncertainty is not code volume. It is PeTTa runtime behavior at composition/marshalling seams and whether the local models produce sufficiently reliable schema-constrained code/repair candidates.

The acceptance gates, not the estimate, determine completion.
