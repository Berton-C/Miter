# 3. Runtime and service topology

## 3.1 Processes

The PoC contains four runtime classes.

### A. Miter core process

- SWI-Prolog running PeTTa/MeTTa;
- owns all meaning-bearing cognition;
- loads immutable Soul and mutable derived organization;
- communicates with local services through imported Prolog predicates under `effect_membranes/`;
- contains no Python client, helper, callback, `py-call`, or Janus path for core services;
- has no generic shell and no raw service secrets.

### B. LM Studio service

- already installed on the host;
- exposes localhost OpenAI-compatible or native REST endpoints;
- serves one chat model at a time or according to available host memory;
- serves a separate embedding model when memory indexing/querying occurs;
- may use LM Studio model load/unload or idle TTL outside the cognitive core.

### C. ChromaDB service

- runs as a newly pinned Miter container or separate local process, not the existing ClarityOmega Chroma instance;
- persists in a separate Docker volume or approved dedicated bind mount;
- is accessed over HTTP by `effect_membranes/miter_chroma.pl`;
- contains the new collection `miter-ltm-v1` and may access an existing NRC VAD collection only through a read-only legacy endpoint or verified copy;
- never shares writable persistence with ClarityOmega;
- is not the only copy of canonical history or continuity data.

### D. Extension Workshop Broker

- runs only when extension work is active;
- owns worktrees, candidate file writes, test/build commands, container access, and diff generation;
- receives typed, allow-listed requests;
- runs generated executable code only in an isolated environment;
- cannot modify `constitution/`, normative documents, or the active core directly;
- cannot promote without a human-approved promotion token.

## 3.2 Core process permissions

The Miter core may read:

- repository source and normative docs;
- immutable Soul;
- current runtime projections;
- canonical event and memory records;
- local model/service status;
- approved module manifests.

The core may write only through named membranes to:

- append trajectory events;
- append memory records and summaries;
- atomically replace current derived projections;
- create candidate module records;
- submit extension-workshop requests;
- prepare, but not directly perform, external effects.

- monotonic local sequence number plus globally unique event ID;
- fsync/atomic append policy defined by `effect_membranes/miter_store.pl`;
- no in-place editing;
- corrupt-line detection without discarding later valid lines;
- hash chain or equivalent integrity link across sequence;
- periodic snapshots are projections, not replacement history.

A developmental experiment may fork trajectory and repository state.

A fork event records:

- parent trajectory event;
- candidate ID;
- worktree path;
- source commit;
- purpose;
- allowed permissions;
- expected tests.

A merge/promotion event records:

- candidate and fork;
- complete test package;
- diff hash;
- human approval where required;
- promoted commit/module version;
- rollback target;
- current active registry change.

A discarded fork remains historically visible.

## 5.4 Status and panic

`panic` prevents any new external effect commit and stops the extension broker while preserving stores. It does not delete state.

# 6. Continuity of Mind architecture

## 6.1 Memory planes

### Plane 1 — trajectory memory

The append-only record of what actually happened. This is authoritative for event history, provenance, development, and prior interpretation.

### Plane 2 — structured continuity memory

Exact active projections that answer questions such as:

- What projects are active?
- Where did we stop?
- What artifact was being changed?
- What is the next intended step?
- What remains unresolved?
- Which commitment is due?
- What module/version is active?
- What did Miter learn and why?

### Plane 3 — semantic long-term memory

ChromaDB indexed documents and chunks used for similarity retrieval, metadata filtering, full-text retrieval, and project/topic recall.

### Plane 4 — raw artifacts

Books, drafts, source code, notes, transcripts, test evidence, and other documents remain at stable paths or content-addressed storage. Memory records point to them; they are not replaced by embeddings.

## 6.5 Existing Chroma migration

The user's current ClarityOmega/Iter Chroma container and writable persistence are not Miter's primary service and must remain untouched. Miter starts with a newly pinned service and fresh, separate persistence. Existing assets must never be opened first against an unpinned new Chroma version.

Bootstrap procedure:

1. locate the current data directory and version;
2. stop all writers;
3. create a byte-for-byte backup and hash manifest;
4. start a Chroma server against a copy;
5. verify collection list, counts, known sentinel records, and known VAD entries;
6. record whether schema migration occurred;
7. keep the original untouched until all tests pass.

Miter's `miter-ltm-v1` collection exists only in its isolated service and persistence. Any inspection server must run against a verified copy. Legacy import or read access is optional after the seed PoC and never creates shared writable persistence.

## 6.6 Existing NRC VAD collection

The existing `nrc_vad_full` collection or local lexicon may be used read-only. It is a licensed local asset and must remain outside the repository.

VAD lookup must prefer exact term/MWE retrieval. Nearest-neighbor semantic matches must not be presented as lexical scores for the original term.

## 6.7 Memory RNA species

### `MemoryCandidateRNA`

Decides whether an event has durable memory value and creates a candidate with type, provenance, scope, and source links.

### `ConsolidationRNA`

Combines related events into an episode, decision, project checkpoint, or learned procedure without deleting the raw events.

### `RecallRNA`

Constructs query text, metadata filters, exact-ID requirements, and source-verification obligations. It receives candidate recalls from Chroma and returns a ranked, provenance-bearing set.

### `ContinuityRNA`

Maintains project capsules, active commitments, current derived module versions, and restart rehydration.

### `ContextRNA`

Builds the bounded context projection for a specific RNA or LLM request.

# 12. Reactor and helical progression

## 12.1 Functional loci

The PoC phase topology is:

```text

→ Orient
→ Recall
→ Transcribe
→ Inquire / Render / Develop
→ Contrast
→ Admit
→ Translate
```

Not every event traverses every locus. Each movement records its actual path.

## 12.2 Ready set

A process is ready only when:

- its dependencies are satisfied;
- its scope remains valid;
- budget remains;
- no higher-priority interrupt blocks it;
- its promoter/eligibility condition is present;

If the ready set is empty, the reactor records quiescence and waits for:

- external event;
- due commitment;
- completed model/service request;
- endogenous interest becoming eligible;
- consolidation due;
- repair opportunity;
- human start/resume command.

# 14. NACE capability-efficacy loop

## 14.1 Minimal role

NACE learns which of at least two eligible voice-repair modules is more effective for a context class.

## 14.2 Belief shape

The implementation may use the existing `(stv frequency confidence)` representation, but exact fields must be read and written using proven scalar-safe patterns.

## 14.3 Outcome evidence

Fixed evidence mapping must distinguish:

- confirmed: module repaired the named defect without causing another material defect;
- disconfirmed: module failed or introduced a material defect;
- ambiguous: evidence is insufficient or evaluators disagree;
- malformed: module did not produce valid output;
- inapplicable: context was outside declared domain.

Only confirmed/disconfirmed feed the minimal revision; other statuses are recorded without forced polarity.

## 14.4 Writer discipline

The belief writer must:

1. read current frequency and confidence as separate scalars;
2. call explicit native `Truth_Revision` or the exact proven wrapper;
